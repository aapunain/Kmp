# Architecture

Clean architecture over Kotlin Multiplatform, targeting Android, iOS, desktop (JVM),
web (JS + Wasm) and a Ktor server.

The reasoning behind every rule below lives in [docs/adr](adr/). Read the ADR before
proposing a change to a rule; the ADR explains what the rule is protecting against.

## Layout

```
app/          entry points: androidApp, desktopApp, iosApp, webApp, shared
contract/     HTTP contract shared by the clients and the server
core/         architecture layers: domain, data, network, concurrency
presentation/ UI and ViewModels
server/       Ktor backend
build-logic/  convention plugins and the executable architecture rules
docs/         this directory, plus ADRs
```

`core/` is a **directory, not a module**. There is no `core/build.gradle.kts` and no
`:core` project. A module named `core`, `common`, `util` or `shared` cannot be held to a
charter, because those names describe a position in the dependency graph rather than a
responsibility, so nothing is ever out of scope for them. See
[ADR-0003](adr/0003-no-catch-all-modules.md).

## Dependency direction

All arrows point inward. `:core:domain` has **zero** dependencies — not coroutines, not
a DI framework. That is deliberate and enforced; see
[ADR-0004](adr/0004-domain-has-no-dependencies.md).

Two consequences worth knowing, because they are enforced by the compiler rather than by
review:

- `:presentation` does not depend on `:core:network`, so `ApiResult` and the wire DTOs are
  not on its compile classpath. It is impossible for an HTTP status code to reach the UI.
- Implementations in `:core:data`, `:core:network` and `:presentation` are `internal`, so
  `:app:shared` cannot name them. Those modules therefore publish their own DI wiring.
  `:core:domain` has no internal implementations, so its wiring lives in the composition
  root instead. Ownership of wiring follows visibility.

## Adding a module

Answer these before creating one. If you cannot, the code belongs in an existing module.

1. **State the charter in one sentence**, in the form "X does not belong here." If you
   cannot complete that sentence with something a person could plausibly get wrong, the
   module has no boundary and should not exist.
2. **Does it have two or more consumers?** One consumer means it is an implementation
   detail of that consumer. Put it in an `internal` package there instead.
3. **Name it for its responsibility**, never for its position.
4. Add it to `settings.gradle.kts`, to `moduleGraph`, and to `moduleCharters`.
   `architectureCheck` fails until all three agree.
5. Run `./gradlew architectureDocs` and record an ADR.

## Where the rules actually live

| Rule | Enforced by |
| --- | --- |
| Module dependency direction | `./gradlew architectureCheck` |
| Every module has a charter | `./gradlew architectureCheck` (cross-checks `settings.gradle.kts`) |
| This document matches the code | `./gradlew architectureDocsCheck` |
| Public API is explicit and intentional | `explicitApi()` in the `kmp.library` convention plugin |
| `Dispatchers.IO` never reaches common code | `./gradlew conventionsCheck` |
| Versions come only from the version catalog | `./gradlew conventionsCheck` |
| Formatting | `./gradlew spotlessCheck` |
| Behaviour on every platform | `./gradlew verify` |

Prose in this file describes *rules and intent*. Anything describing *current state* is
generated. That split is the whole reason this document can be trusted: see
[ADR-0001](adr/0001-record-architecture-decisions.md).
